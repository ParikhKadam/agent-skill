Clarity-first planning

A planning partner that helps you understand a feature before you document it, and keeps what you learn in small, linkable docs that are easy to change.

Why it exists

Three things go wrong again and again when a team plans a feature by writing a detailed spec first.

The world was not what was assumed

Fields that do not exist, data half-filled, an old test copy of a system. Nobody checked until the build was far along.

Guesses were written as decisions

The spec said how autonomous a model should be, and the build later moved to plain code. Nothing could say which was better.

One-shot build

When intermediate results are not stored, users cannot redo one part, and nobody can build, test or improve one piece alone.

The skill's answer: get clarity first, in a fixed order, with a check (a gate) at each step, and write docs that explain why, not only what.

What a session looks like

  1. Orient. It reads your code and docs, finds or creates a planning folder, and restates the outcome and size back to you for a yes.
  2. Ask a round. Every question that is unblocked now (usually around ten), grouped by theme, each with its recommended answer worded so "yes" accepts it. It looks up what it can instead of asking you.
  3. Record. What it learned goes into the right small doc, with a status: decided, hypothesis, unknown or measured.
  4. Check the gate. When the layer's check is met it summarizes in plain words, shows the evidence, and asks you to agree.
  5. Hand back. What is now understood, what is open (with owners and defaults), and the first step next time.

Stages you can run on their own

The layers are grouped into stage skills. Each can be invoked by itself. They depend on each other only through the planning folder: an earlier stage writes docs and passes gates, and a later stage reads them. Say "plan this feature" and the hub runs the stages in order, asking you before each new stage. Name a stage and it runs alone, first checking whether the earlier layers are settled.

SkillLayersNeeds firstWrites
plan-clarity0-3nothingbrief, glossary, cases, facts, constraints, risks, spikes, decisions, open questions
plan-components4-6clarityuser flow with re-entry points, artifacts and staleness, one doc per component

If a stage is invoked before its prerequisites pass, it tells you what is still open and what that risks. You choose to go back, or to proceed with the gaps recorded as hypotheses. No layer is marked done without your explicit yes. When something cannot be checked yet (no data access, the other team unreachable), you can pass a step with conditions; each condition becomes early work in the build plan.

The twelve layers

Pick a size to see which layers run. Small features skip most; large ones run all of them in full. The order is by cost of being wrong times uncertainty, which is why facts and risks come before flows.

1Outcome and valueWho acts on the result? What would make them distrust it? Which part carries the value?Two or three real cases have a hand-written ideal result you recognize

5Artifacts and stalenessWhich intermediate results are stored, and what makes each stale?Every re-entry has an artifact; every stale rule has a decided behavior
6ComponentsWhat produces each artifact? Who decides inside: code, model or person?Each runs alone from stored inputs and has a quality bar and test set

Where the docs live: a hierarchy, not one long document

One feature gets one folder of small docs grouped by what a reader wants to know. Nobody reads everything: each doc names the reading paths it belongs to, and a generated index lists every doc.

docs/planning/<feature>/
  INDEX.md              every doc, with summary, status, version and what it rests on
  html/                 three reading pages for people who do not open markdown
  00-start/             brief, glossary, hand-written cases      (what and why)
  10-world/             facts register, existing system, limits   (what is true outside our design)
  20-risks-and-decisions/  risks, spikes, one file per decision, open questions
  30-behavior/          user flow, artifacts and staleness, system flow
  40-design/            one file per component, cross-cutting, one file per contract
  50-plan/              implementation plan, one file per slice
  90-log/               layer gates, change log, session notes

Reading paths

onboard (10 minutes), understand, review, build-component, contract, change-request. Ask for one and get just those docs.

The index

Generated, never hand-edited. Status by layer, reading paths, every doc, decisions by confidence, open questions with owners, and a health list.

Staleness by pins

Each doc records the version of what it rests on. Change one doc and the checker lists every doc written against the old version.

What makes the docs different

Usual specThese docs
States: "Actions are capped at 8."Explains: why 8, what evidence, what would change it.
Everything reads as decided.Every claim carries a status: decided, hypothesis, unknown, measured.
Organized by section number.Organized by what a reader wants to know; each doc has a one-line summary for the index.
One long file.Many small files, one decision, component or contract each, with stable ids.
Rewritten when requirements move.Edited in place; an impact command lists what to reopen; the change is logged.

The tools

A small script, scripts/wsctl.py, handles the mechanical parts so the conversation can stay on understanding. It uses only the Python standard library.

CommandWhat it does
init, newCreate a workspace sized small, medium or large; add a decision, spike, component, contract, case or slice from a template
statusWhich layer you are on, what is open, what may be stale
checkLint: re-entry points with no artifact, components with no quality bar, contracts with no failure example, decisions with no tripwire, layers passed without evidence
index, htmlWrite the detailed index and the three reading pages
read-set, impactList the few docs needed for one purpose; list every doc that rests on a changed doc

See it working

The folder examples/invoice-capture/ is a finished workspace for an invented feature (invoice capture with approval and ERP posting). Open its overview page, flows page and plan page to see what the generated pages look like. It passes the checker with no warnings.
