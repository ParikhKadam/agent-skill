User flow, with re-entry points agreedv2

In plain words

The clerk uploads an invoice and sees what the system read, which PO it matches and what codes it proposes. The clerk can fix any of those, redo one part, or pick the PO directly. When satisfied, the clerk sends it to a manager, who approves or rejects. Approved invoices post to the ERP.

The story, step by step

Walked with CASE-02 (partial delivery, approver away).

  1. The clerk uploads the PDF. The system shows the extracted fields beside the PDF.
  2. The clerk fixes a misread total (a correction). The fields are saved.
  3. The system proposes the PO and flags "3 of 10 lines not yet received". Because the receipt is short, the clerk must record a decision: hold, or approve as billed with a reason.
  4. The system proposes accounting codes. The clerk changes one code.
  5. The clerk sends for approval. The system routes it to the manager's delegate, because the manager is on leave.
  6. The delegate approves. The record shows who approved, as delegate for whom.
  7. The system posts to the ERP (after checking nothing was posted before) and shows "posted" with the ERP reference.

Other paths

  • Alternate paths: no PO number (CASE-03: candidates are listed and the clerk picks); the clerk already knows the PO and skips the automatic match.
  • What differs by role or permission: clerks upload, fix and send; managers and delegates approve within their limit; nobody approves an invoice they uploaded.
  • When something fails, and how the user recovers: an unreadable scan shows "could not read this invoice; enter it by hand". An ERP outage leaves the invoice "approved, not posted" and it retries.
  • When the user leaves halfway and comes back: everything is saved at each step; the invoice reopens where it was.

Re-entries ruled out

  • Skipping the read step: the fields are needed for everything after; the clerk can correct them instead.
  • Regenerating an approval: it is a person's decision, never generated.
  • Editing a posted invoice: reversal is a separate ERP process, out of scope.

System flow agreedv1

In plain words

A full run reads the PDF, matches, proposes codes, waits for approval, then posts. Because every result is stored, a re-run starts from any of them, and posting always checks first for an earlier post.

A full run

  1. C-extractor reads the PDF and writes ART-01. Decides inside: a model, judged against hand-checked fields.
  2. C-matcher reads ART-01 and live PO and receipt data and writes ART-02. Decides inside: code, with the clerk picking leftovers.
  3. C-coder reads ART-02 and writes ART-03. Decides inside: rules from the supplier's coding history.
  4. A manager approves (ART-04). Decides: a person. The invoice waits in "awaiting approval".
  5. C-poster reads ART-04 and, in order: re-checks ART-02 against live data, looks up an earlier ERP post, then posts and writes ART-05. Decides inside: code.

Nothing runs in parallel in version 1: each step needs the artifact before it. Coding could run alongside the approval wait only if codes were not part of what the manager approves, and they are (D-004).

Duplicates, retries and concurrency

  • The same upload twice: caught by a hash of supplier, invoice number and total; the clerk sees the earlier invoice.
  • Two clerks open the same invoice: the first holds a lock; the second sees "being edited by X".
  • A retry after a timeout: the lookup finds the earlier post, so no duplicate.
  • A failed step never stores a partial result as if it were complete.

Components

Coder

C-coderagreed

Proposes account and cost-centre codes for each invoice line (ART-03) from the supplier's coding history

Who decides: Code (rung 0): the most frequent codes for the same supplier and item description; the cost centre from the PO. A model is not used. If a supplier is new, the codes are left empty with "no history" for the clerk to fill.

Extractor

C-extractoragreed

Reads the PDF and produces the extracted fields (ART-01); a model, judged against hand-checked invoices

Who decides: A model (rung 2: one call, no tools). Rungs 0-1 were considered: templates per supplier do not scale. Output is validated by code (the total must equal the sum of lines; dates must parse). The model never sees bank details.

Matcher

C-matcheragreed

Finds the supplier and PO for an invoice (ART-02) with exact rules, and lists candidates when the rules cannot decide

Who decides: Code (rung 0), by decision D-001. Rules in order: exact PO number; else one PO for that supplier within 5% of the total. Everything else becomes a candidate list for a person. A model for the leftovers was considered and deferred; the measured evidence (S-001) does not justify it yet.

Poster

C-posteragreed

Posts an approved invoice to the ERP once, checking first for an earlier post (ART-05)

Who decides: Code (rung 0). Steps in order: confirm the approval is still valid (D-004); re-check the PO is still open and the receipt unchanged; look up supplier plus invoice number in the ERP; post only if none exists.
